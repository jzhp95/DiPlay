## 1. 产品定义

### 1.1 要构建的运行系统

系统在已有认证、配对与 CarPlay 会话之上，完成：

1. 协商可支持的视频能力并核验实际输入。
2. 接收屏幕数据、认证解密、拆包和组装访问单元。
3. 保持配置与帧身份，限制输入积压。
4. 选择合格解码后端，持续送入并及时排出视频帧。
5. 根据解码后像素的实际语义完成必要的颜色处理。
6. 将最新有效画面提交给车机显示链路。
7. 独立处理真实触控并发送给 iPhone，形成交互闭环。
8. 在切模式、切 Surface、断开、异常时可靠退役资源并恢复。

iPhone 负责 CarPlay 内容生成与编码。车机 App 不能直接控制手机编码器内部实现，
不能假定能力声明一定成为实际编码、分辨率或持续帧率。

### 1.2 成功条件

- 颜色：已知参考下保留近黑、近白和彩色层次，无不应有的范围扩张、灰阶截断、
  通道错误或重复颜色转换；真实 CarPlay 输出在目标配置中得到验证。
- 跟手：输入派发、命令写出、视频接收、排队、解码、绘制各段无持续失控积压；
  实际操作响应达到用户接受的目标，并区分局部指标和完整触摸到显示测量。
- 稳定：长时间运行、反复切屏／重连时对象和缓冲有界，释放失败可识别，
  不会把“等待上一连接释放”伪装成已解除。
- 可追溯：每个实际后端、颜色契约、回退和恢复动作都有身份和理由。

“可播放”“测试完成”“颜色正确”“跟手达标”是不同状态。
没有任何后端同时达标时，允许系统继续提供明确标识的兼容播放，
但不能宣称最终产品目标已经完成。

### 1.3 范围

- 第一阶段独立实现主屏视频运行模块，保持既有协议接入、音频、麦克风与车辆按键接口；不调用旧视频管线或旧 renderer 完成新主屏流程。
- 主屏以既有 type=110 语义接入；不改变其他屏幕角色的配置归属。
- H.264 和 HEVC 使用统一契约，编码支持及颜色适用范围分别标明。
- 不从零编写 H.264／HEVC 熵解码、运动补偿等完整算法；首期使用平台硬／软解，成熟原生软解仅作为可选阶段 D。
- 不重写 MFi／配对安全协议，不在性能优化中改变密钥、认证或消息计数规则。
- 不恢复已删除的独立应用、BYD／DiLink 或其他车型专属适配。
- 不通过全局强制 Limited、Full、BT.709 或亮度滤镜掩盖问题。

## 2. 已有证据与设计依据

### 2.1 颜色

历史已知 Full 固定素材的软件直出 P3／P4 用例出现：

| 参考灰阶 | 实际截图 |
| ---: | ---: |
| 4、16 | 0 |
| 224 | 242 |
| 235、236、238、240 | 255 |

它支持错误 Limited 扩张后的截断形态，不能定位到具体内部组件。
最新用户反馈是：早期软件直出正常，最新版直出等组合发白，
软件 YUV＋跟随视频颜色可接受；强制 Limited 会变差。
该反馈与历史固定素材数值分开保留，不虚构回归提交或把原因归给 iPhone。

### 2.2 性能

旧真机 H.264 动态样本中，局部队列到输出均值分别约为：

- 硬解 Surface：11.71ms。
- MTK YUV：39.95ms。
- 软件 YUV：94.62ms。

固定 1080p60 运动素材中，硬解 Surface 接近 60fps，
两条 YUV 路径约为 42fps，并出现明显排队。
这些是设计的调查依据，不是新管线性能承诺；
它们也不是完整触摸到显示延迟，不能据此认定纯解码或 VSync 各占多少。

### 2.3 由证据得到的约束

- 先建立明确的像素语义与生命周期，不能用改几个参数替代运行架构。
- 避免网络接收、输入送入、输出排出、EGL swap 互相串行阻塞。
- 改进应用积压不等于消除源编码、codec 内部缓冲或系统显示队列。
- 已经被解码器或显示转换截断的灰阶，后续 Shader 无法恢复。
- “重写”本身不证明能够规避所有厂商驱动行为。

## 3. 主要架构决策

| 决策 | 选择 |
| --- | --- |
| 协议和认证 | 沿用现有 CarPlayController／AirPlaySession／ScreenStream 的已验证职责 |
| 视频入口 | 在 MediaSink 视频接口后引入可替换的运行模块 |
| 状态管理 | 每个主屏视频会话一个协调器，控制操作串行化 |
| 并发 | 接收、解码输入、解码输出、渲染分别拥有明确职责 |
| 输入缓存 | 有界访问单元队列，按帧、字节和年龄共同管理 |
| 自绘输出 | 一个进行中帧＋一个最新待显示帧，不累积待绘制列表 |
| 颜色 | 输入声明、解码输出、转换决策和目标显示空间分别建模 |
| 后端 | 硬解直出、硬解 YUV、原生软解 YUV；保留平台软解作兼容与回归对照 |
| 选择依据 | 能力、颜色资格、已知故障与延迟策略共同决定，不按“硬解必然最好”决定 |
| 恢复 | 过期输出丢弃、参考链恢复、codec 重建和整会话重启分级处理 |
| 集成 | 旧新模块可切换，每个会话只允许一个模块拥有生产视频 |
| 默认启用 | 新模块先显式启用；目标车机验收通过前不替换默认 |

## 4. 端到端运行流程

~~~mermaid
flowchart TD
    A[iPhone 生成并编码画面] --> B[USB 网络或 Wi-Fi]
    B --> C[ScreenStream 接收与认证解密]
    C --> D[配置解析与访问单元规范化]
    D --> E[有界压缩帧队列]
    E --> F[解码后端]
    F --> G[合格硬解 Surface 直出]
    F --> H[硬解或软解 YUV 帧]
    H --> I[输出像素描述与颜色决策]
    I --> J[最新帧槽与 EGL 渲染]
    G --> K[Android 合成与车机显示]
    J --> K
    L[真实触摸] --> M[坐标映射与独立 HID 队列]
    M --> N[事件通道写出]
    N --> A
~~~

控制平面负责能力、配置、后端与代际；
数据平面只传递本代际的配置、访问单元与输出帧租约。
轻量诊断订阅有界元数据副本，不拥有或阻塞生产数据流。
颜色取证另设显式同帧采样钩子：在生产帧租约有效期内、纹理上传前读取同一实例的像素，
只将有界样点副本交给异步导出；不另起 decoder 冒充生产像素，详见第 23.2 节。

## 5. 连接、协商与会话启动

### 5.1 连接层

沿用现有 USB／NCM 或无线网络接入、认证与配对流程。
视频模块不直接操作 USB 端点、热点、手机配对存储或 MFi。
接入适配器接收已建立会话的屏幕流和触控发送能力。

启动顺序：

1. SessionRuntime 创建正式连接请求快照。
2. 现有控制协议协商屏幕参数、编码能力并建立屏幕流。
3. 新模块获得 sessionId 和 streamRole，初始化入口代际。
4. 收到有效 CSD 后解析实际编码、尺寸、位深、颜色和参考帧需求。
5. 根据输出目标及后端资格创建解码会话。
6. 请求或等待合法随机访问点。
7. 收到有效帧并完成首次显示提交后发布视频活动状态。

### 5.2 能力承诺

- 只有确认存在并可配置的编码能力才能声明支持。
- HEVC 开关是请求／允许策略，实际编码由收到的流确认。
- 不支持 HEVC 软解时不能宣称已提供 HEVC 软件后端。
- 请求帧率是上限能力，不写入“手机实际选择 60fps”的推断结果。
- 不为降低延迟默认改变用户分辨率或画质。
- 持续过载时，只有用户开启质量降级策略，才允许通过正式会话重新协商更低负载；
  结果必须记录并可见，不能偷偷改变同一对照组条件。
- 高位深、HDR、宽色域或超出本阶段支持的格式应明确拒绝、降级协商或保留既有路径，
  不能按 8bit SDR 公式直接显示。

## 6. 核心数据模型与接口

以下为接口语义草案，不是要求直接复制进代码的实现。

### 6.1 身份

~~~text
VideoIdentity
  sessionId
  streamRole
  streamGeneration
  configGeneration
  decoderGeneration
  surfaceGeneration
  backendInstanceId

FrameIdentity
  VideoIdentity
  accessUnitId
  decodeOrder
  sourcePts? / sourceDts?
  codecPtsUs
  receivedLocalNs
~~~

- 配置、解码器和 Surface 代际互相独立，不能复用一个计数器表达所有变化。
- 所有回调携带原始身份；旧代际不能覆盖新状态。
- 手机时间、codec PTS 与本机单调时间分别保存，不混用。

### 6.2 输入配置与访问单元

~~~text
VideoStreamConfig
  codec / codecProfile / codecLevel
  csdOwnedBytes / csdSha256
  codedSize / displayCrop
  bitDepth / chromaSubsampling
  sourceColorDeclaration
  parseStatus
  sourceFraming

EncodedAccessUnit
  identity
  ownedBufferLease / offset / length
  randomAccessKind
  sourcePts? / sourceDts?
  receiveStartedNs / receiveCompletedNs
  configurationHash
~~~

访问单元借用的数据在所有权移交后不可修改。
使用 offset／length 视图减少切片，但不能引用下一次读取会覆盖的临时数组。

### 6.3 解码输出

~~~text
DecodedFrameLease
  frameIdentity
  backendKind / componentName
  codedSize / crop / rotation
  presentationPts
  outputPixelDescriptor
  storageKind
  planeViews? / nativeFrameHandle?
  releaseOnce()
~~~

storageKind 为 PLATFORM_IMAGE、NATIVE_YUV 或 OPAQUE_SURFACE。
OPAQUE_SURFACE 不伪造可读取的 plane。

每个 PlaneView 描述：

- buffer／native 地址的有效生命周期、起始偏移和有效长度。
- rowStride、pixelStride、平面宽高。
- 坐标原点是完整编码帧还是裁剪后区域。
- 采样精度、位深及 UV 顺序。

只有真实可访问的平面才能构造 PlaneView。
所有几何与长度计算先使用宽整数验证，防止乘法、偏移和裁剪溢出。

### 6.4 后端接口

~~~text
VideoBackend
  capabilities()
  configure(config, outputTarget, options) -> ConfigureResult
  trySubmit(accessUnit) -> Accepted | Backpressure | Rejected
  pollOutput(deadline) -> DecodedFrameLease | FormatChanged | NoOutput | Failure
  requestStop()
  awaitReleased(deadline) -> Released | StillRetiring
~~~

- configure 成功不等于已经输出正确画面。
- Accepted 表示已接收所有权，不表示已经解码或显示。
- MediaCodec 输入线程与输出线程可以并行，但 configure／flush／release
  只能由协调器按生命周期屏障执行。
- 原生后端不默认支持 submit／receive 并发；共享的原生解码上下文由一个执行器拥有，
  在同一循环中交替送入／排出，再向渲染线程交付租约。

### 6.5 上层接口

~~~text
VideoRuntime
  attachSession(sessionIdentity)
  onConfig(config)
  tryOfferAccessUnit(accessUnit)
  attachOutput(outputTarget)
  detachOutput(surfaceGeneration) -> ReleaseTicket
  setRuntimePolicy(policy)
  stop(reason) -> ReleaseTicket
  snapshot() -> VideoRuntimeSnapshot
~~~

控制命令为异步、有身份和幂等语义。
媒体回调不能同步等待 configure、显示、文件写入或释放。

## 7. 协调器状态机

主状态：

~~~text
IDLE
 → WAIT_CONFIG
 → SELECT_BACKEND
 → CONFIGURING
 → WAIT_RANDOM_ACCESS
 → RUNNING
 → RECONFIGURING / RECOVERING / SURFACE_SUSPENDED
 → STOPPING
 → RELEASED
~~~

异常状态：

- DEGRADED：仍可播放，但颜色资格、性能或画质不满足全部目标，必须列出原因。
- UNSUPPORTED：无可用格式／后端组合。
- BLOCKED_RELEASE：旧资源未真实释放；不允许创建相冲突的新资源。
- FAILED：已停止，原因和资源退役状态可查询。

同一个协调器内，同一时刻只允许一个活动配置提交者。
重复配置以内容哈希去重；真正变化才增加 configGeneration。
普通重复 CSD 不应反复重建解码器。

首次输出超时、输出格式变化、解码失败、Surface 丢失分别有独立事件；
不统一解释成“重连手机”。

## 8. 线程与锁

| 执行单元 | 拥有的职责 | 禁止执行 |
| --- | --- | --- |
| 屏幕接收线程 | 读包、协议校验、认证解密、轻量移交 | GPU、等待 codec、同步日志归档 |
| 视频协调器 | 生命周期、后端决策、代际、恢复、租约状态 | 在持锁状态 join native 线程 |
| MediaCodec 输入线程 | 顺序提交访问单元、处理输入 backpressure | EGL 绘制或持事件写锁 |
| MediaCodec 输出线程 | 持续排出、建立输出租约、管理最新待显示帧 | 等待 UI／公共目录 Binder |
| 原生解码执行器 | 原生 decoder 的 send／receive 与解码上下文 | 多线程无序访问同一上下文 |
| EGL 渲染线程 | 上下文、纹理上传、绘制、swap、渲染资源销毁 | 网络读取和 HID 写出 |
| 既有输入发送线程 | 手势队列、事件写锁及实际写出 | 等待视频渲染 |
| 有界诊断写线程 | 抽样、轨迹和归档 | 反向阻塞生产媒体回调 |

线程是会话拥有的可回收资源，不为每帧新建线程或 executor。
音频与麦克风保持独立所有者，不与视频共用会被 swap 阻塞的执行器。

锁规则：

- 不同时持有协议／事件锁和 codec／EGL 生命周期锁。
- 不在持管理锁时等待线程退出、GPU、Binder 或文件系统。
- 跨线程传递所有权用租约和代际，不能依赖未经声明的共享可变字段。
- 关闭协议先使阻塞 I/O 可退出，再等待媒体资源。
- 取消只改变请求状态；最终 released 取决于真实资源完成。

## 9. 接收、解密与组帧

现有 ScreenStream 使用 128 字节头、独立视频／配置 opcode，
最大 body 为 8 MiB；新适配器保持相同协议语义，不在重构中改变线协议。

顺序：

1. 检查消息长度和来源归属。
2. 完整读取受限 body，记录接收完成时间。
3. 按现有算法认证解密，成功后按既有规则推进消息计数。
4. 区分配置与视频访问单元。
5. 检查 NAL 封装、长度、配置归属与支持的访问单元边界。
6. 必要时执行一次 AVCC／HVCC 到 Annex-B 规范化。
7. 以已拥有的缓冲或安全视图移交，避免后续再次全量转换。

拒绝超长／截断／认证失败的数据；不得继续使用未认证载荷。
不得为“丢旧帧”跳过必须推进的加密计数，不得因重建 codec 重置仍在使用的流密钥计数。
同一协议流中的解密与密码学计数必须保持顺序。

当前回调可能运行于媒体归属保护范围，tryOffer 必须快速返回：
仅做有界移交，不在回调里同步请求关键帧、释放 codec 或等待渲染。

H.264 的 SPS／PPS、HEVC 的 VPS／SPS／PPS 通过已验证的解析路径处理。
不假定一个 NAL 就是一张完整画面，不丢失 B 帧所需的解码／呈现顺序语义。
不能从源 PTS 缺失时伪造源节奏，配置解析失败保留原因。

## 10. 输入队列与参考链

### 10.1 初始容量

以下是初始工程保护参数，不是“达到该值就证明手感合格”的阈值：

| 项目 | 初始上限／策略 |
| --- | --- |
| 单条协议 body | 沿用 8 MiB |
| CSD | 256 KiB |
| 待解码访问单元 | 最多 8 个且不超过 8 MiB |
| 控制邮箱 | 有界；Stop 由原子状态和唤醒保证，不被普通帧挤掉 |
| 待应用配置 | 只保留最新配置及其合法代际屏障 |
| 渲染待处理帧 | 1 个，另允许 1 个进行中帧 |

实际缓冲必须计入全局应用所有预算，不能各队列分别分配上限后无限叠加。

### 10.2 短突发与持续过载

允许网络短突发，不因一帧变老或一次队列峰值就重建 codec。
持续积压结合以下事实判断：

- 实际源／到达节奏。
- 最老待解码帧年龄与队列深度趋势。
- 输入与输出是否继续推进。
- 渲染是否被阻塞。
- 当前是否处于启动、静止画面或显式节奏模式。

初始策略可采用至少 300ms 的持续趋势窗口与 500ms 的输入硬年龄保护，
并受帧／字节硬容量约束；实施须用数据调整，不能当作目标延迟承诺。
不同恢复动作要限频并形成 episode，不能每个旧帧都触发一次关键帧请求。

**静止与唤醒子状态**：与连接健康、参考链有效性分别建模。

- 初始静止判定窗口为 3 秒，作为可调整工程参数记录，不是协议超时。
  仅在没有新视频访问单元、应用输入及输出待处理均已排空、没有未完成 codec 工作，
  且会话未报告传输故障时进入 QUIESCENT；最后有效画面继续显示。
  这只表示视频暂时安静，不证明手机或网络健康，连接心跳／断线检测保持独立。
- 在 QUIESCENT 停止无输入条件下的 codec 无进展计时，不清除合法参考链，不请求关键帧，
  不清空源颜色／配置，也不把静止时长累计到积压趋势。
- 首个新访问单元到达时进入 RESUMING，重置本轮积压趋势与推进基线。
  年龄按每个访问单元自身的本机单调接收时间计算，不按上一显示时间或源 PTS 空档计算。
  首个恢复帧不因此前的静止间隔触发 R1／R2；不强制要求它是关键帧，原参考链有效时可继续解码。
- RESUMING 在开始正常推进后回到 ACTIVE；持续过载判断重新收集至少 300ms 的趋势，
  不能带入静止前的旧 episode。唤醒突发仍遵守帧数、字节和实际帧年龄硬上限，
  不提供无限豁免；解码错误、失效参考链和协议故障仍立即按真实原因处理。
- 若无新输入但仍有待解码／待渲染数据，不能进入 QUIESCENT 掩盖卡住。
  突发到达的帧即便内容较旧，其源端等待也不能凭本机接收年龄测出，须单独记录可用时钟证据。
- 导出 activityState、lastInputArrivalMonoNs、idleDurationMs、resumeEpisodeId、
  resumeFirstFrame 与恢复触发原因；缺少源端测量时不把 idleDuration 当端到端延迟。

### 10.3 压缩帧过载

- 不随机清除任意 P／B 帧后继续假装参考链有效。
- 无法保留完整依赖时，失效当前链、释放相关输入、保留最新合法配置。
- 请求随机访问帧并等待后端支持的合法随机访问点。
- 参考链只在访问点实际提交成功后恢复。
- HEVC 的不同随机访问类型及 leading pictures 必须按实际支持处理；
  不支持安全从 CRA 恢复时，不得把所有 IRAP 一概当作无条件 IDR。
- 应用队列等待不等于 codec 内部耗时，单独计数。

## 11. 解码后端

### 11.1 硬解直出：PlatformSurfaceBackend

- 通过 MediaCodec 配置目标 SurfaceView。
- 解码输出由独立排出线程尽快决定显示或丢弃。
- 丢弃使用正常归还输出 buffer 的方式，保持 codec 内部参考链。
- 需要定时呈现时使用 API 28 可用的机制，禁止使用高版本专有接口而无保护。
- CSD 本身包含源声明；显式 MediaFormat hint 是独立可追溯策略，
  “没有额外设置 hint”不能解释成“decoder 没收到任何颜色信息”。
- 只对有适用资格的组件／颜色配置启用为自动首选。
- 输出 Surface 的原始 Image 不可直接取得，不伪造三层同实例像素链。
- Texture 输出保留为实验／兼容变体，不在未验证时与 SurfaceView 当作完全等价。

### 11.2 硬解可读 YUV：PlatformYuvBackend

- 选择已确认的硬件组件，配置受支持的 CPU 可读 YUV 输出。
- 原始 Image 仍以真实 plane 布局处理，不根据格式名称猜 NV12。
- 每个输出 buffer 构造一个具有释放责任的帧租约。
- 硬件输出范围／矩阵可能与源声明不同，必须经过输出像素契约解释。
- 可读 YUV 不支持、图像为空或布局无法安全访问时，标为后端不支持或失败。
- 不能回退到直出后仍报告 hardware_yuv。
- 该后端不是颜色自动正确的保证；用户已反馈它在当前场景仍发白。

### 11.3 原生软解：NativeSoftwareYuvBackend

选择成熟的 FFmpeg libavcodec／libavutil 作为拟接入组件，通过 JNI 提供 H.264／HEVC
软解能力；这是新的视频后端，不是自研两种压缩标准的完整算法。

定位为阶段 D 的中长期可选后端，默认关闭，不是短期颜色修复或发布的前置条件。
短期先修复和验证现有平台硬／软解及直出／YUV 路径，保留已确认的软件 YUV＋跟随视频基线。
强制 Limited 只作受控对照；用户已反馈该选项会发白，不能将它推广为默认修复。
五模式诊断足以组织现有路径对照，但能否定位具体截断环节仍取决于同帧证据是否齐全。

阶段 D 必须单独评估和交付：

| 风险 | 必须满足的条件 |
| --- | --- |
| 许可证与分发 | 审计实际源码、配置和链接依赖；计划采用不启用 GPL／nonfree 组件的 LGPL 构建及独立共享库，附许可证、对应源码／补丁、构建方式和适用的替换／重链接材料；由实际分发方案确认合规 |
| 包体增量 | 对锁定版本的最小 arm64 构建实测 SO、剥离符号后大小、APK 压缩增量及运行依赖；3～5 MB 只能作为待验证的预算估计，不能写成所有构建的必然下限 |
| Native 崩溃 | 同进程 SIGSEGV／abort 不可由 Java catch 或 JNI 错误码可靠兜底；未隔离部署时明确承认整个进程可能退出，不承诺无感回退 |
| 算力与热稳定性 | 在目标车机测 H.264／HEVC、实际分辨率／帧率、线程 CPU、持续吞吐、温度与降频；不预设需要几个大核或必达 1080p60 |
| 工期与维护 | 独立安排依赖裁剪、交叉编译、JNI 所有权、安全加固、混淆、运行与长期压力验证；未完成不进入默认后端候选 |

许可证边界：静态链接本身不等于自动变成 GPL；动态链接本身也不免除合规义务。
实际许可取决于启用的组件和分发方式，参见
[FFmpeg 官方许可说明](https://ffmpeg.org/legal.html)。

JNI 需做句柄／代际、边界、长度、整数溢出、引用与线程检查，并覆盖畸形码流、
native 内存检查及崩溃记录。若产品要求 decoder native 崩溃后主 UI 与会话进程存活，
则必须另立独立进程隔离设计和验收：包括 IPC、共享内存／帧租约、死亡通知、
资源回收及重建成本；不把它暗含在当前同进程 JNI 接口里，也不假定它没有延迟成本。

- 只构建所需 decoder、parser 和基础工具，不引入编码器、网络协议或完整播放器框架。
- 实施依赖清单必须锁定有维护的稳定版本、源码 SHA256、构建选项和补丁，
  完成许可证／分发条件审核；未完成则不得合入或启用该后端。
- 仅 arm64-v8a，API 28，项目既定 NDK，不使用构建机器专属指令。
- 使用实际可用的 ARM64 优化；不以开启 O3 或某宏作为性能已提升的证明。
- 原生输出 YUV 平面以引用计数租约暴露，能安全直接上传时不先复制到 Java ByteArray。
- JNI 传递结构和句柄，不逐帧构造完整 RGB Bitmap。
- 支持内存受限的 send／receive、flush、drain、错误上报和释放。
- 不默认使用尽可能多的 frame threads；此模式可能增加帧缓冲延迟。
- slice／frame 线程策略按实际码流能力与结果选择，不能通过一个 low-delay 标志保证零缓冲。
- B 帧／DPB 的合法重排不能为了“低延迟”而错误关闭。
- 如果软解吞吐不足，明确进入降级状态或经授权重协商，不无限增加线程和队列。

### 11.4 平台软解兼容：PlatformSoftwareYuvBackend

旧管线保留现有 Google 平台软解＋应用 YUV 作为效果回归基线；
新管线的平台软件后端则使用自己的 PlatformYuvBackend、帧管理、颜色和 EGL renderer，
不调用旧视频类完成播放。平台软件组件可相同，应用实现与资源所有者必须独立。
NativeSoftwareYuvBackend 不冒充同一个后端，也不静默替换诊断中的“平台软件 YUV”。

诊断五模式保持其既定语义；原生软解是额外专项 profile，
未单独获得用户确认前不把五模式自动扩展为六模式，也不混算历史 CPU／延迟结果。

## 12. 帧与 buffer 的所有权

### 12.1 统一规则

- 每个已出队的 codec buffer 必须立即有唯一所有者。
- buffer、Image、原生 AVFrame 引用、暂存平面、纹理是不同资源。
- releaseOnce 负责防重释放；失败仍向恢复流程传播，不当作成功。
- “已尝试归还 buffer”与“codec 已实际销毁”分开记录。
- buffer 归还失败不再重试同一 index，转入该 codec 的恢复／销毁流程。
- 不能在释放失败后递增显示成功、标记首帧成功或报告颜色完成。

### 12.2 MediaCodec YUV 所有权转移

1. 输出线程取得 index 和 Image。
2. 创建租约并发布到最新帧槽。
3. 替换尚未渲染的旧租约时，归还旧 Image 和 buffer。
4. 渲染线程取得待显示租约，只在持有期间读取 plane。
5. 纹理上传已不再依赖源像素后，关闭 Image 并归还 buffer。
6. GPU 绘制／swap 继续执行，不再占用已无依赖的 codec 输出资源。
7. 异常路径同样完成清理；保留原始错误及附加清理异常。

第 5 步的安全性必须按使用的上传 API 及内存来源验证；
使用异步 GPU／原生互操作时须等相应 fence，不得套用普通客户端内存上传的假设。

### 12.3 原生帧

- 原生帧句柄含 generation 和引用状态。
- 原生 decoder 的 DPB 引用与应用持有的显示引用分别管理。
- 丢弃显示引用不能破坏 decoder 所需的参考帧。
- Java 对象被 GC 不是释放正确性的主要机制。
- 应用停止后不允许外部回调访问已 unref 的原生地址。

## 13. 颜色语义与决策

### 13.1 四份描述分别保留

~~~text
SourceColorDeclaration
  range / matrix / primaries / transfer
  bitDepth / chromaLocation
  origin=SPS_or_other_protocol
  parseStatus

DecoderOutputDescription
  reportedRange / reportedStandard / reportedTransfer
  planeLayout / crop / bitDepth
  actualComponent
  reportAvailability

ResolvedPixelContract
  effectiveRange / effectiveMatrix / effectiveTransfer / effectivePrimaries
  evidenceBasis
  confidence
  applicabilityKey
  conflictReasons

RenderTargetDescription
  pixelFormat
  EGLConfig / requestedColorSpace / actualAvailability
  windowOrSurfaceDescription
~~~

源 SPS、MediaFormat 标签、实际像素和窗口目标不是同一个对象。
不能把 output 字段缺失改写成已经确认的 Full／Limited。

### 13.2 决策顺序

1. 明确用户手动覆盖时记录覆盖内容，作为实验参数，不扩展为全局自动修复。
2. 应用经验证、适用于当前组件／格式的像素契约；记录为什么能使用它。
3. 对标准且可靠的后端采用其定义的输出语义，并与源声明交叉核对。
4. 冲突、未知组合或可疑厂商报告保留 unknown／conflict，
   选择已知可用的兼容路径或报告资格不足，不从地图画面亮度猜范围。
5. 不能简单规定“永远 SPS 优先”或“永远输出标签优先”。

资格记录必须限定设备构建、codec 组件、编码 profile／位深、源颜色组合、
输出布局、后端与颜色算法版本。手机更换配置或组件更新可使旧资格失效。

### 13.3 数学处理

对于 8bit SDR YUV，使用对应真实范围的归一化；
Limited 亮度使用 16／219，色度使用 128／224；
Full 使用完整码值范围及正确色度中心。
矩阵至少正确覆盖已声明支持的 BT.601 与 BT.709 系数。

转换得到的 R′G′B′ 与其 transfer／primaries 语义须保持一致，
避免再无依据地做一次 gamma 或范围扩张。
不能把 matrix=6 自动替换为 BT.709 只为匹配 Android 某个复合 standard 常量。
同样不能把所有非 709 矩阵都静默当作 601。

HDR、宽色域、高位深需要独立处理契约；本阶段不具备时明确不支持，
不能用 SDR clamp 冒充 tone mapping。

### 13.4 截断与不可逆性

- 在错误转换发生前修正语义。
- 若原始输出已经把多个参考灰阶合并，后续逆变换不能找回原值。
- 不使用自然画面直方图自动确认像素范围。
- 固定灰阶正常只是必要条件，彩色色块、实际流与窗口路径仍需验证。
- 用户画面调节属于额外后处理，必须可旁路；不能作为核心颜色修复。

## 14. EGL 渲染与显示提交

### 14.1 最新帧槽

- 只有渲染线程能取得“进行中”租约，输出线程不得在它使用过程中关闭该租约。
- 输出线程可替换一个尚未开始的待显示租约，被替换者立即归还。
- 不在渲染线程上等待下一输入帧；无新画面时保持当前有效显示。
- EGL 上下文、窗口、程序和纹理由同一所有者创建和销毁。
- viewport、裁剪、旋转和触控变换使用同一显示几何快照。

### 14.2 纹理路径

| 输入布局 | 首选处理 |
| --- | --- |
| 紧凑平面 YUV420 | 三平面纹理上传，避免中间 RGB |
| 已确认共享布局的 NV12／NV21 | 两平面纹理及正确 UV 顺序 |
| 带 padding／非紧凑平面 | 安全的按行重排或平台支持的上传方式 |
| 布局未知 | 使用通用平面描述校验；不能安全解释则拒绝该后端 |
| Opaque Surface | 不进入 CPU YUV 上传器 |

pixelStride=2 本身不能证明 U／V 两个 ByteBuffer 可以安全组成连续 NV12。
两纹理路径也不是零 CPU 或零驱动拷贝的承诺。

在 GLES 2.0 上不能假定存在 GLES 3.0 的任意行跨度上传能力。
行缓冲、staging 和纹理按尺寸复用；格式／尺寸变化时有界更新。
不逐帧创建 Bitmap、程序、纹理或 DirectByteBuffer。

### 14.3 上传、归还与呈现

分开记录：

1. 获得渲染租约。
2. 必要的像素读取／重排。
3. 纹理上传及其内存依赖结束。
4. 归还 Image／codec buffer／原生显示引用。
5. 绘制。
6. 交换缓冲。
7. 可获取的 Surface 渲染回调。
8. 外部实际屏幕呈现测量。

这些时间不能互相冒充。
未验证 GPU fence 语义前，不引入异步内存互操作。

**现有生产配置与新模块继承要求**：当前 SoftwareYuvRenderer 在 EGL 上下文设为 current 后
已调用 EGL14.eglSwapInterval(display, 0)。YUV 自绘路径沿用请求值 0，
不在新模块重建时无故恢复为 1，也不再把现有配置描述成尚未采用的实验项。
用户在本次复审中报告跟手改善，作为实车主观反馈记录；尚不能仅凭这条反馈
断言改善全部由单项配置造成，或所有后端的颜色与完整触控延迟均已通过。

硬解 SurfaceView 直出不经过该 EGL renderer，沿用平台 MediaCodec／Surface 的呈现机制；
不对它套用此 eglSwapInterval 配置或声称已关闭系统合成同步。

后续实现需记录请求值、EGLConfig 的最小／最大允许值、调用返回／错误和 swap 实际耗时。
当前代码调用本身不等于已经具备以上观测。EGL 允许按配置范围钳位请求值，
因此不把“请求 0”记录为已知的有效值 0；BufferQueue／GPU 压力仍可能阻塞。
不能据调用成功就宣称不再等待或已经省下一个 VSync。
若某设备需改为同步配置，应由明确的兼容策略和对照结果决定，保留回退依据。
规范语义见 [EGL 1.4](https://registry.khronos.org/EGL/specs/eglspec.1.4.pdf)。

## 15. 新鲜度与呈现调度

### 15.1 低延迟默认

默认在解码、颜色准备与输出目标有效后尽快提交。
不为平滑隐藏加入固定多帧延迟。
用户明确选择的节奏模式属于独立策略，记录其引入的目标等待。

呈现顺序基于 decoder 输出 PTS 和本代际状态；
不能在显示较新 PTS 后又显示旧 PTS，合法重排不能按网络到达顺序简单覆盖。

### 15.2 丢弃已解码旧帧

允许丢弃不再需要呈现的已解码输出，以保持 decoder 的压缩参考链。
必须满足生命周期和显示连续性要求：

- 不把启动首帧、唯一静止画面或最后一个有效画面无条件丢弃。
- 不能规定“所有年龄超过 30ms 的帧都丢弃”。
- 存在明确更新画面时，保留最新可用帧，释放未开始绘制的旧帧。
- 只怀疑将来可能有新画面时，有界等待或保留当前帧，不无限等更新帧。
- 诊断定格和显式节奏模式采用其独立语义。
- 丢弃前不做无意义的 YUV 全量重排或 GPU 上传。

“输出槽只保留最新”只限制应用级显示积压，
不能消除 codec 内部已存在的重排／缓冲时间。

### 15.3 避免恢复振荡

每次积压建立有界 episode，记录起止、深度、年龄、动作和恢复结果。
优先使用轻量动作；硬错误或无进展才升级。
不能在同一 episode 连续 flush、重建、请求关键帧，造成恢复本身反复制造停顿。

## 16. 时钟、帧率与音画关系

- 本机阶段统一使用单调时钟，保留原 Android eventTime 和转换依据。
- 手机 PTS／NTP 保留为源时钟，未建立映射时不得直接减本机时间。
- 即使存在相对节奏锚定，也不宣称建立了精确跨设备时钟同步。
- 到达帧率、提交帧率、decoder 输出帧率和显示提交帧率分别统计。
- 静止内容降低输出或源重复画面，不自动视为掉帧。
- maxFPS 是能力上限，不能替换实际源节奏。
- 原有音频时钟和播放策略保持独立；视频重构不能偷偷改变音频缓冲。
- 显式音画同步或节奏策略应单独标明其等待，避免将有意等待归入纯解码成本。
- 局部 Surface 回调或 swap 返回不等于物理面板完成扫描。

## 17. 触控返回链路

### 17.1 坐标与会话归属

触摸事件携带：

- sessionId、主屏控制 token、surfaceGeneration。
- Android 事件时间、应用收到时间。
- 完整 pointer 集与动作。
- 当前视口／黑边／旋转／裁剪变换版本。

先将屏幕坐标映射到当前 CarPlay 逻辑内容，再按既有 HID 协议编码。
黑边和测试控制按钮不能当作手机内容坐标发送。

### 17.2 队列与优先级

- 复用既有独立输入发送职责，不与视频或 EGL 共用执行器。
- 相同手势中尚未发送的冗余移动事件可合并。
- 按下、抬起、取消、pointer 集变化不能作为普通移动丢弃。
- 队列按数量、年龄和会话身份限制。
- 旧会话、旧屏幕 token 或过期几何输入拒绝并记录原因。
- 实际写锁等待、write 和 flush 与本地接收分别计时。
- 写出完成不代表手机已处理，不伪造 ACK。

切 Surface／模式时优先通过仍有效的旧通道完成有界手势收尾。
不能为了发送收尾一直阻止连接关闭；通道已失效时结束本地旧手势并记录不确定状态。

### 17.3 闭环边界

运行链路是：

    用户触摸 → 本地派发 → HID 写出 → iPhone 处理
    → 新视频到达 → 解码 → 颜色处理 → 显示

系统拥有其中一部分时间戳，不拥有全部。
完整实际响应仍需要可靠的触摸与显示对应测量；运行模块不制造总延迟数字。

## 18. Surface 与配置变化

### 18.1 Surface 变化

- 新 Surface 产生新的 surfaceGeneration，不改变源颜色配置代际。
- 旧 Surface 的待绘制租约失效，进行中资源按所有权退出。
- 原始 YUV 后端可以在源配置不变时仅更换 EGL 目标，不必每次重建 decoder。
- 直出后端只有在输出目标类型和使用方式兼容时才尝试 setOutputSurface。
- 切换失败通过正常 codec 退役与重建恢复，不能忽略失败继续报告新屏已绑定。
- Surface 被销毁前提供实际释放票据；超时只表示仍未确认。
- 新屏首次显示需要合法可解码画面时，通过独立控制通道请求恢复。

### 18.2 配置变化

CSD、编码、位深或解码相关尺寸真正变化时：

1. 停止接收旧配置帧进入新 decoder。
2. 丢弃旧显示待处理项并保留必要的最后状态说明。
3. 退役旧 decoder 和相关租约。
4. 创建新 configGeneration 和 decoderGeneration。
5. 重新决定像素契约与后端资格。
6. 从支持的随机访问点恢复。

不能因同一 CSD 重复出现而重复重建。
只有显示窗口大小变化时优先改变 viewport，不改变源解码尺寸。

## 19. 后端资格、选择和回退

### 19.1 能力与颜色资格分开

capability=available 只表示可以创建和运行，不表示颜色正确。
每个后端记录：

- capability：available／unsupported／failed。
- qualification：unverified／fixture_verified／live_verified／user_observed。
- applicabilityKey：目标设备构建、组件、后端算法、源格式、位深、颜色组合与输出种类。
- knownFailures、最近失败动作和有效期依据。

普通 APK 的 UI 变化不必自动否定所有像素资格；
颜色算法、decoder、驱动、输出配置或适用输入改变时必须重新评估。
资格版本与 APK 身份分别记录，不能用一个布尔值永久表示“该车机颜色已好”。

### 19.2 自动选择原则

在自动模式下：

1. 优先选择具有适用颜色资格、能力有效且无当前硬失败的硬解 Surface。
2. 直出不合格时考虑具有适用像素契约的硬解 YUV。
3. 需要软解时，在已完成资格与性能核验的原生后端和平台兼容后端之间选择。
4. 已验证颜色基线优先于只因延迟数字小而未经验证的路径。
5. 没有同时达标路径时，提供明确的兼容／降级状态，保留可用控制和音频，
   不编造“自动选择已同时解决颜色与延迟”。

用户明确强制实验后端时可运行可支持组合，但必须显示真实后端和未验证状态。
结构不合法、内存不安全或不支持的格式仍不能强行运行。

### 19.3 后端切换事务

- 停止当前输入接纳或切到受控配置屏障。
- 停止旧输出发布，释放待渲染项，等待进行中租约收尾。
- 确认旧资源退役后创建新后端；未释放不能同时创建替代者竞争资源。
- 后端切换增加 decoderGeneration，原网络流的加密计数继续按协议运行。
- 新后端不能随意从依赖旧参考的 P／B 帧开始。
- 等待随机访问点后再恢复正常显示。
- 尝试次数有界；同一失败组件不在一个会话内被无限自动重选。
- 切换失败保留原因与最后有效结果，必要时回到用户确认的旧实现。
- 不因后端局部失败直接破坏配对、认证或重置网络配置。

### 19.4 画质／帧率降级

默认只报告持续过载，不偷偷降低分辨率或请求帧率。
用户允许降级时，生成新的正式协商请求，记录新的实际源参数。
诊断对照中一旦发生此变化，该样本标为条件改变，不能与原配置直接比较。

## 20. 分级恢复

| 等级 | 条件 | 动作 | 不应执行 |
| --- | --- | --- | --- |
| R0 | 更新已解码帧可用，显示待处理帧过时 | 丢旧输出，保留最新 | 任意清除压缩参考帧 |
| R1 | 应用压缩队列参考链已失效 | 失效旧链、请求随机访问帧 | 每次都销毁 codec |
| R2 | codec 硬错误、持续无进展、输出布局失效 | 退役／重建或选择其他合格后端 | 未确认释放就启动替代实例 |
| R3 | 屏幕流协议失效、认证解密失败、连接断开 | 由正式会话控制器关闭／重建流 | 媒体线程自行修改密码学计数 |
| R4 | native 释放或 EGL 退出无法确认 | BLOCKED_RELEASE，停止资源竞争 | 以计时器伪造 released |

“无新画面”先判断源是否本来静止，不能把正常静止内容当成硬卡死。
故障和恢复有最小必要的有界历史，不持续保留全部帧或完整 Throwable 列表。

## 21. 停止与资源释放

### 21.1 全连接关闭

沿用控制器先使阻塞 I/O 可退出的顺序：

1. 标记当前连接和视频入口不再接纳新工作。
2. 关闭需要用于解除阻塞的 socket／传输。
3. 使输入发送、媒体回调和接收线程能够退出。
4. 视频协调器停止输入、停止输出发布并收回待显示租约。
5. 等待进行中的像素使用结束，归还 Image／codec buffer／原生引用。
6. 停止并释放 decoder。
7. EGL 所有线程销毁纹理、程序、窗口和上下文。
8. 退出工作执行器，清理监听器、池中借用、回调及诊断订阅。
9. 发布真实资源释放结果。

不得在同一持锁范围执行关闭 socket、等待媒体、等待输入写锁的相反顺序。
主线程和 UI 不执行无限 join。

### 21.2 退役与超时

- released 状态只在相关资源确实结束后成立。
- 已退出对象从 retiring 注册表及时移除。
- 超时仍活跃的 native 资源继续跟踪，但禁止无限创建替代资源。
- 不让已退出对象继续保留大输入队列、PCM／YUV 暂存或 Activity 回调。
- 迟到输入和回调不能重新填充已停止队列。
- 应用进程重启不自动恢复一个未完成的诊断批次或无意图地重连。

## 22. 内存和资源预算

以下为初始应用拥有内存的硬保护设计，实施时需要验证峰值；
不把平台 codec／GPU 内部分配算作“免费”。

| 类别 | 初始预算 |
| --- | ---: |
| 接收密文暂存 | 8 MiB |
| 解密后 AU 池，含排队／解析／移交借用 | 合计 16 MiB |
| 应用持有的解码帧／显示引用 | 合计 24 MiB |
| 纹理上传重排暂存 | 8 MiB |
| 控制、指标和诊断轻量环形数据 | 4 MiB |
| 应用模块保护总额 | 64 MiB，含余量 |

- 这些是共享预算，不保证每个子项都可同时额外分配一份上限。
- 接收预算不足先对输入产生受控 backpressure，不继续隐式分配。
- 无法保持完整协议处理时结束屏幕流并交给正式会话恢复，不任意跳过认证和推进计数。
- 本阶段以现有目标分辨率为能力基线，不无条件接受所有 4K／高位深输入。
- 尺寸、stride、crop 和有效长度均验证；超预算拒绝配置或通过正式策略降级。
- pool 有明确最大数量和容量，尺寸降低后可按生命周期回收高水位缓冲。
- decoder 内部 DPB、原生分配、图形缓冲、纹理、Surface 和线程分别计数与观察。
- 不从未释放 native 内存的假设出发无限扩大 Java heap。
- 内存进入平台缓存高水位与对象持续累积要分别判定，不能把 RSS 上涨都叫泄漏。
- 诊断开关关闭时，不持有原始全帧、长视频或无界 JSON 轨迹。

## 23. 运行指标与证据接口

### 23.1 常态轻量指标

- 实际输入 codec、尺寸、源声明、输出描述、后端与资格依据。
- 接收／提交／解码／丢弃／显示提交计数和对应时段。
- 输入队列深度、字节、最老年龄，显示槽状态及 QUIESCENT／RESUMING 活动状态。
- 应用等待、输入 buffer 获取、codec 输出等待、像素重排、上传、绘制、swap。
- 输入派发、HID 排队、写锁和写出。
- CPU 单核等效值、关键线程 CPU 与墙钟耗时。
- 活动与 retiring decoder／Image／lease／Surface／线程／池借用数。
- 恢复 episode 与后端切换理由。

均值以正确计数器作分母，缺样本为 null。
滚动分布有容量上限，不因样本满了停止更新。

### 23.2 显式诊断

区分两类采集，二者不能混称为零开销旁路：

**轻量旁路统计**：默认仅消费计数、时间戳和格式等有界元数据副本，
不延长生产 Image／AVFrame 生命周期，不访问已释放的 plane，不在视频线程同步写盘。
用于吞吐、排队和耗时分布，不据此判灰阶正确。

**侵入式同帧颜色采样**：用户显式开启，在渲染线程持有生产帧租约时，
在纹理上传和颜色转换前，从这一个 Image／PlaneView／原生帧读取指定样点。
样点与该帧的源声明、实际 decoder、输出描述、颜色契约和转换参数绑定；
仅把复制完成的小型不可变样点交给有界异步导出，之后按正常流程归还原帧，
不把原 plane 或裸指针交给异步文件线程。
初始限制为每帧最多 64 个 patch 点、每秒最多 2 帧、每次最多 10 秒；
上限是工程保护，不能据此声称无性能影响。记录采样次数、耗时、丢弃数和开关状态。

RGB 需在同一生产渲染实例、同一 frameId 对应的绘制结果上获取并关联；
例如有界读回该帧渲染目标，显式记录 GPU 同步成本和采集位置。
窗口截图若不能证明对应 frameId，只能标 association_unavailable，不能算同帧配对。
渲染目标 RGB 不等于物理面板测量，屏幕合成／显示后的效果另行标注。
性能基准使用关闭侵入采样的时段，采样时段单独报告，不混算“无诊断干扰”结果。

硬解直出无法从该生产实例读取 Image 时，明确 raw_yuv_unavailable；
另一 decoder 读出的 YUV 只能是不同实例的辅助证据，不能提高为同实例完整。
同帧证据缺失或导出丢弃时判 partial；采样失败不能阻塞生产或伪造成功。

支持受控订阅：

- 同一短段原始视频与配置，具有可回放索引和随机访问边界。
- 同一实例可读取时的真实 YUV、RGB 与对应帧身份。
- 不能获取的原始像素、dataspace 或呈现时间明确 unavailable。
- Surface 旁路参考实例明确标为另一实例。
- 事件有本地时钟类型和代际，能区分源 PTS、到达、解码和显示提交。
- 原始帧和文件写入使用有界异步能力；诊断慢不能拖住生产视频。

证据完整不等于画面正确。该接口只提供真实数据，
分析与判定沿用已知参考、同源对照和校准后的测量边界。

## 25. 迁移与兼容策略

### 25.1 双实现，单会话拥有者

- 旧 AndroidVideoPipeline 保持可用。
- 新实现通过设置“视频管线”显式选择，原有管线默认、新管线实验性，选择发生在新会话创建边界，详见第32节。
- 同一主屏流只能交给一个生产视频实现，不能同时运行两个播放器比较。
- 观察模式只能订阅有界元数据；重放分析使用独立诊断身份，不冒充实时生产实例。
- 回退恢复原实现及用户设置，不影响配对、音频、方控和已保存报告。

### 25.2 分阶段

| 阶段 | 交付 |
| --- | --- |
| A | 固化契约和适配入口；旧实现作为基线，功能行为保持 |
| B | 新协调器、有界输入、MediaCodec 后端、资源退役与触控几何 |
| C | 像素契约、EGL 渲染、最新帧调度、同帧证据 |
| D（中长期可选） | 原生软解独立评估与接入；许可、包体、崩溃边界、ABI／R8、热稳定性和性能全部过门禁后才可启用 |
| E | 同源码流对照、颜色回归和生命周期故障注入 |
| F | 目标车机颜色＋跟手共同验收，再决定默认切换 |

A～C 可独立进入 E／F 验证，不等待 D；E 的对照先覆盖实际已实现后端，
D 后续加入时另走其专属门禁。原生软解不是现有颜色修复的唯一解或短期阻塞项。
每阶段是否可用与最终验收分别记录。
原生依赖或硬件资格没通过时，该阶段保持关闭，不把未实现项包装成已支持。

### 25.3 与已确认五模式的关系

既有五模式属于当前实现的诊断语义。
新模块的 profile 必须增加 implementationId 和 backendKind，
避免新版原生软解结果覆盖旧平台软件 YUV 的记录。
历史软件直出正常版本的 APK／提交需要独立保留以追查回归，
不能用新模块某个模拟配置代替真正旧版。

### 26.2 功能与故障用例

至少覆盖：

- 分片读取、消息超长、认证失败、配置重复、CSD 变化、迟到旧会话帧。
- AVC／HEVC 封装、合法随机访问、重排、缺配置、损坏长度。
- 满输入队列、短突发、持续积压、静止画面和首帧。
- 静止超过 3 秒和几十秒后恢复：首帧为关键帧／普通依赖帧、合法突发、配置变化，
  均不因静止时长误触发 R1／R2；真实堵塞和唤醒后持续过载仍被检出。
- 一个进行中帧时反复替换待显示帧，所有被替换资源准确归还。
- Image 获取、上传、绘制、swap、releaseOutputBuffer 各阶段抛异常。
- 原生句柄提前释放、重复归还、旧 generation 回调、DPB 引用和显示引用独立。
- 行跨度、pixelStride、奇数 crop、UV 顺序、plane 长度及乘法溢出。
- Full／Limited 合法转换与错误扩张、601／709 彩色色块、transfer 冲突。
- Surface 失效、兼容／不兼容切换、无新帧时销毁、后台再进入。
- write 锁阻塞、socket 关闭、停止期间输入、pointer 变化和几何变化。
- decoder 卡住／未退出、渲染线程卡住、停止超时、不启动替代者。
- 组件不支持、回退后身份变化、原生组件缺失和格式不支持。
- 尺寸变化、长时间运行、反复连接、资源与内存高水位／累积区分。
- 原始诊断订阅慢、写盘失败、缺字段、0 字节文件不影响生产和成功判定。
- 同帧采样的实例／frameId 关联、异步导出不持有原 plane、采样开销分离及采样不完整判 partial。

### 26.3 颜色验收

- 使用已知参考与实际码流重建值，不从照片平均亮度判原始范围。
- 复现历史 Full 灰阶截断；错误实现应被回归用例检出。
- 同时验证近黑、近白、中性灰与彩色色块。
- 参考、YUV、RGB 必须同帧／同实例或明确标注旁路边界。
- 只在具备校准容差和实际参考时输出 reference_match。
- 输出标签正确不能代替像素正确，固定样本通过不代表全部真实输入正确。
- 目标组合必须包含手机曾出现的 primaries=1、matrix=6、transfer=13；
  不只用标准 BT.709 灰阶证明所有场景。
- 目标车机最终窗口与用户实际显示反馈纳入验收。

V07 编码差异专项：同一手机、同一可重现画面、同一显示几何和目标渲染路径，
分别建立 H.264 与 HEVC 会话，按实际输入而非 HEVC 设置值分组。
历史观察到 H.264 matrix=6、HEVC matrix=1，必须覆盖这两个组合；
这不是所有 iPhone 固定不变的规则，每次仍解析真实 SPS／VUI。
另记录范围、primaries、transfer、实际 decoder／回退与输出描述，
任何其他变化均列为条件差异，不把综合结果单独归因于编码格式。

两种编码的“矩阵选择一致性”指同一决策规则正确处理各自声明与像素契约，
不是强制两者使用相同矩阵。原始像素契约与声明一致时分别采用 601／709；
存在解码端转换或经验证冲突时记录其适用契约，不盲目只信 SPS。
对每种编码独立配对参考→同实例 YUV→RGB，检查近黑、近白、中性灰与彩色 patch；
对同画面应用各自参考与压缩容差，不要求有损编码间逐字节一致。
不能建立同源／同帧参考或某路径 raw 不可读时，明确相应证据边界，不能标完整通过。
本专项独立于真机一次运行五模式的约定；单次五模式仍固定 HEVC 开或关，
不静默把用户的一次测试扩成十组。

### 26.4 跟手性与性能验收

- 分别报告源到达节奏、应用排队、codec 输出、重排／上传／绘制／swap。
- 报告分布、长间隔、恢复频率、实际帧率、CPU 和温度，不只报告均值。
- 不将帧线程增加吞吐误判为低延迟改善。
- 不在颜色已失败的模式上用低时延宣称整体达标。
- 同输入、同设备、同配置比较新旧模块。
- 完整触摸到显示需要可靠关联或外部测量；没有时明确未测。
- 具体可接受延迟需由有效旧版基线与目标车机实测确定，
  本规格不编造 11ms、30ms 等总链路通过线。
- 若没有可比较正常基线，不能宣称“已恢复原来手感”。

## 27. 风险、失败解释与产品状态

| 风险 | 处理原则 |
| --- | --- |
| 驱动已经截断像素 | 不做逆滤镜伪修复，换配置／后端，必要时兼容软解 |
| 输出标签与实际语义不符 | 依据适用像素契约和已知参考，未知时不自动猜 |
| 原生软解增加包体或维护成本 | 中长期可选 D 阶段，实测增量并核查分发条件，不阻塞 A～C 修复 |
| 原生 decoder 发生致命崩溃 | 同进程无法保证存活；若要求主进程存活，单独设计进程隔离及 IPC 成本 |
| 静止恢复被误认成积压 | 本地逐帧接收年龄、独立唤醒趋势和真实连接健康判定 |
| 颜色取证影响性能 | 侵入采样显式限量、同实例绑定、开销分段，关闭采样后测性能 |
| 软解算力不足 | 报持续过载，经授权重协商；不靠无限缓存和线程 |
| Surface 路径不可读 raw | 承认测量边界，不能拿另一实例 raw 冒充 |
| GPU 或 codec native 卡住 | 阻止新资源竞争，保留真实退役状态 |
| 源参数中途改变 | 新配置／代际与重新资格核验 |
| 新旧结果存在诊断干扰 | 记录观察开销，隔离捕获与动态测量阶段 |
| 本地测试通过但车机仍异常 | 功能保持实验，继续基于实际像素定位，不宣称硬件天然无问题 |
| 没有同时合格的后端 | 明确目标尚未完成，保持可用兼容路径和回退能力 |

对用户可见的状态至少区分：

- 正常播放，实际后端可查。
- 兼容播放，列出未满足项目。
- 等待关键帧／恢复画面。
- 等待真实资源释放。
- 格式不支持或连接中断。
- 新模块未完成目标车机验收。

应用不能为了显示绿色而隐藏回退、改画质、抹掉灰阶问题或填造延迟。

## 31. 新管线独立实现边界（v1.2 必须遵守）

本节落实用户明确要求：不是在旧 YUV 管线上换调度器，也不是包装旧类改名。
H.264／HEVC 解码算法使用成熟组件；视频运行架构由本项目独立设计并实现。
YUV 是像素格式，使用它不代表复用旧实现。

### 31.1 共用与禁止依赖

| 边界 | 允许 | 禁止 |
| --- | --- | --- |
| 连接和认证 | 既有 USB／无线、配对、MFi、认证解密和协议计数 | 新视频线程私自改密钥／计数或热点 |
| 已认证视频入口 | ScreenStream／MediaSink 交付的数据及明确流身份 | 再次认证或对已 Annex-B 数据重复长度前缀转换 |
| 访问单元和配置 | 新入口模块自己管理组帧、配置、封装、归属及缓冲；审计合格纯标准解析可共用 | 以旧 decoder／plan 状态决定新运行状态 |
| 解码能力 | MediaCodec 和经独立评估的成熟原生库 | 从零实现 AVC／HEVC 压缩标准 |
| 主屏视频 | 全新 coordinator、queue、backend、frame lease、color、renderer、metrics | 调用 AndroidVideoPipeline／SoftwareYuvRenderer 完成新主屏播放 |
| 像素和颜色 | 全新 PlaneView、读取器、像素契约和shader实现 | 直接引用旧 Yuv420Frame／SoftwareYuvColor 作为新内部实现 |
| 调度与恢复 | 新状态机、最新帧槽、新鲜度和生命周期 | 委托旧 VideoOutputFreshness／VideoPlanResolver 或拷贝整个旧类改名 |
| 输入回传 | 新几何、手势调度；共用协议编码和最终 writer | 被旧视频线程／EGL锁阻塞，或复用旧视频状态 |
| 音频与外围 | 保持既有 audio、麦克风、车辆按键、定位接口 | 为视频重写外围功能或引入其他车型逻辑 |
| 报告文件 | 共用已验证的最终写盘、回读和归档组件 | 用旧decoder的采样结果冒充新生产实例 |

纯函数复用白名单必须具体到符号、输入输出和测试，不笼统写“图像处理可复用”。
只允许无decoder／renderer／队列／会话可变状态的标准解析或基础工具。
AndroidMediaSink 可以作为公共门面，但不能在选择新主屏时无条件构造旧主屏实例。
旧 VideoPipelinePlan／VideoOutputObservation 不作为新内部状态契约；外围旧接口如需兼容，
通过显式值转换适配，不回调旧管线完成新路径。

### 31.2 分支和屏幕角色

- 新主屏实现标 implementationId=independent；旧实现标 legacy。
- type=110 主屏选择作用于该会话，不因诊断、回调或输出格式变化偷偷走旧主屏。
- 首期非主屏／mirror 保留独立 legacy endpoint 是允许的，但必须按 streamRole 单独报告；
  它们不能与新主屏共享 decoder、颜色状态或租约。
- LegacyVideoEndpoint 是唯一专门包装旧实现的适配边界；新模块核心不import旧类。
- 自动回退到旧主屏需要结束／退役新主屏并经过会话边界，显示 actualImplementation 和原因；
  原后端 native 仍挂住时不创建竞争实例。
- 把旧主屏工厂在测试中设为拒绝构造，新主屏仍须完成自己的接收、解码、渲染和停止；
  同时检查实际调用链，不能仅看包名或类名不同。
- 用颜色基线作效果对照，不复制该旧实现作为新架构；新实现效果仍需独立验证。

### 31.3 当前协议入口精度

现有 ScreenStream.kt 同文件包含 ScreenCodec，读视频后已经顺序认证解密，
推进 frameCounter，并调用 lengthPrefixedToAnnexB 再交付 listener。
因此首期新入口接收的是已标准化 Annex-B 数据。
新入口独立校验、关联配置和组装访问单元；没有证据不得重复AVCC转换或把一个NAL等同一帧。

如后续要将封装规范化移入新模块，必须另立兼容变更，显式记录入口framing，
同时验证旧／新两支和密码学计数。当前任务不授权修改wire protocol。

## 32. 设置切换与实际运行一致性

### 32.1 设置定义

- 设置名：“视频管线”；位置为现有 ADVANCED_MEDIA 分类，纳入搜索及既有布局规则。
- 两项：“原有管线”（默认）、“新视频管线（实验性）”。
- 缺失、未知或损坏的持久化值选择 legacy，并记录原因，不擅自开启新实现。
- 保存字段为独立版本键，持久化revision保护用户新选择；诊断临时覆盖不写永久设置。
- 设置项同时区分已保存选择、当前请求和实际运行，不把开关状态当实际运行证据。
- 新管线自己的 RuntimePolicy 不复用旧 VideoPipelinePlan。用户现有HEVC、尺寸、
  帧率和颜色请求通过明确值映射；不因为切管线偷偷改变画质或音频。

### 32.2 切换事务

1. 未连接时只保存，下一次正式连接生成不可变快照。
2. 连接中提示会重连，经现有正式 UI command 和 reconfigureFromUi 生成新 SessionStartRequest。
3. 停止旧会话接纳／HID手势，解除I/O阻塞，真实退役视频资源。
4. released 后才为新会话构造所选实现；不能调用仅复用旧requested的reconnect代替重新配置。
5. 卡住则保持BLOCKED_RELEASE并显示原因，不通过超时伪造可重连。
6. 快速重复切换只保留最新待生效请求，旧requestId不能完成新UI状态。
7. 诊断占用时明确拒绝或有界等待；取消和恢复不能覆盖用户更晚revision。
8. 新实现失败时提供切回原实现入口；自动回退若被配置允许，也必须记录请求、
   实际实现和原因，不能无提示当作新实现继续。

视频运行模块与底层连接音频独立不意味着整会话重连完全无音频中断；
实际短暂中断应如实提示，不能承诺无缝。

### 32.3 完整门面要求

当前 AndroidMediaSink 的视频表面不止 onVideoFrame：
还包括 config／codec、Surface绑定／detach、mirror、释放等待／通知、诊断冻结、
raw采样、cadence、backlog、resource counts、recovery handler和观察快照。
实施必须先列全方法和调用者，再做统一角色路由。
公共 SurfaceDetach 不能继续只包旧 AndroidVideoPipeline.SurfaceDetach；
改为后端无关的 ReleaseTicket 语义并保持调用方行为。

新实现不支持的能力明确 unsupported，不返回空成功，不偷偷转旧decoder完成诊断。
AndroidMediaSink 的 audio 所有者与协议接口保持；旧新视频endpoint各自拥有自己的资源。
